# 聊聊 C 语言里的 volatile：到底什么时候该用，什么时候是瞎用

写单片机代码的人，迟早都会碰到 `volatile` 这个关键字。网上的说法五花八门，有说"中断里用到的变量都要加"的，有说"加了就线程安全了"的，还有干脆所有全局变量都糊上一层 `volatile` 图个心安的。我自己也踩过不少坑，这篇就把这些年攒下来的经验捋一捋，希望能帮你少绕点弯路。

## 先说结论

一句话：**只要这个变量的值可能被"编译器看不见的力量"改掉，或者它的读写本身就带副作用，那就必须加 `volatile`。** 别的都是多余的。

## 编译器真的会"骗"你

先别急着背规则，得先搞明白为什么需要这东西。

编译器在开优化（`-O1` 以上）的时候，会做各种推理。比如这么一段：

```c
uint8_t flag = 0;
while (flag == 0) { }
```

编译器一看，循环体里根本没改 `flag`，那它就觉得："我读一次到寄存器里循环判断就行了，没必要每次都去内存读。" 于是生成的汇编大概是这样：

```asm
    LDR  r0, [flag]     ; 只读这一次
loop:
    CMP  r0, #0
    BEQ  loop
```

这在纯软件逻辑里没问题。但如果 `flag` 是中断里改的呢？中断把它改成 1，主循环还用寄存器里的旧值判断，那就是永久死循环。程序看着像卡死了，其实是被编译器"优化"掉了。

`volatile` 的作用就是告诉编译器：这玩意儿随时可能变，每次用都必须老老实实去内存读，写也必须真写回去，不许缓存、不许删除、不许乱重排。

## 什么时候必须用

### 1. 中断和主程序共享的变量

这个是最常见的场景，也是最容易出事的地方。

```c
volatile uint8_t g_rx_flag = 0;

void USART1_IRQHandler(void)
{
    g_rx_flag = 1;          /* 中断里改 */
}

int main(void)
{
    while (g_rx_flag == 0) { /* 主循环等 */
        /* 不加 volatile 的话，这里很可能死循环 */
    }
}
```

判断方法很简单：**变量在 `xxx_IRQHandler` 里被写，在别的地方被读或被写，那就加 `volatile`。** 反过来，如果变量只在中断里读写、外面根本不碰，那其实不用加。

### 2. 硬件寄存器

所有外设寄存器本质上都是内存映射的地址，值由硬件改，必须 `volatile`。而且有些寄存器读一下就清标志（读即清），这时候 `volatile` 更是不可或缺——不然编译器看你读了个变量又没用，直接就给你删了。

```c
#define GPIOA_ODT  (*(volatile uint32_t *)0x40020014UL)
```

厂商头文件里那些寄存器指针全都带 `volatile`，就是这个道理。

### 3. RTOS 里任务间共享的变量

```c
volatile uint8_t g_task_ready = 0;   /* 任务 A 写，任务 B 读 */
```

但这里有个特别容易踩的坑：**`volatile` 只保证"每次都真读写"，它不保证原子性。** 像 `++`、读-改-写这种复合操作，该被打断还是被打断。很多人以为加了 `volatile` 就线程安全了，这是彻底的理解错误。

### 4. DMA 改的内存

DMA 在后台往一块内存里写数据，对 CPU 来说这就是"外部力量"，编译器根本不知道。所以 DMA 缓冲区也得加：

```c
volatile uint8_t dma_buffer[128];
```

### 5. 会被硬件自动改的标志位

比如各种状态寄存器里的 BUSY 位，硬件会自己清掉，这种轮询也得加：

```c
volatile uint32_t *p_status = &periph->status;
while (*p_status & BUSY_BIT) { }
```

## 什么时候真的不用加

下面这些是很常见的误用，加 `volatile` 纯属浪费：

| 场景 | 要不要 | 原因 |
|---|---|---|
| 普通局部变量 | 不用 | 生命周期就在函数内，外部改不了 |
| 只在主循环里读写的全局变量 | 不用 | 编译器能看到全部读写 |
| 数组传给 `memcpy` 之类库函数 | 不用 | 没有异步改变 |
| 想用它做线程安全 | 不用，也没用 | volatile 不提供原子性和内存屏障 |
| 想用它当内存屏障 | 不用，也没用 | C 标准里 volatile 没这语义 |

特别说一句最后两条，这是重灾区。`volatile` 能防编译器优化，但**防不了 CPU 乱序执行，也保证不了读-改-写的原子性**。真要做同步，得用临界区、原子操作或者屏障指令。

## volatile 到底做了什么

理解这三个特性，用起来就不容易错了。

**第一，每次访问都真去内存。** 连续写两次，两次都保留：

```c
volatile uint8_t reg;
reg = 1;
reg = 2;   /* 第一次不会被删掉 */
```

**第二，不优化掉"看似没用"的读写。**

```c
volatile uint32_t *p = &periph->data;
*p;        /* 就读一下扔掉，编译器不会删——因为读可能清标志 */
```

**第三，访问顺序不被重排。** 但要注意，这个保证只在 `volatile` 之间成立，`volatile` 和普通变量之间是没顺序保证的。硬件时序特别严格的地方，还得额外加屏障。

## 几个对照写法

### 中断标志

```c
/* 错：可能被优化成死循环 */
uint8_t g_flag;

/* 对 */
volatile uint8_t g_flag;
```

### 寄存器指针

```c
/* 错：丢掉了 volatile，优化后行为会出问题 */
uint32_t *reg = (uint32_t *)0x40020014UL;

/* 对：volatile 修饰的是"被指向的对象" */
volatile uint32_t *reg = (volatile uint32_t *)0x40020014UL;
```

这里插一句语法上的小坑：`volatile uint32_t *p` 修饰的是指向的对象，不是指针本身。要是想让指针本身 volatile，得写 `uint32_t * volatile p`。搞寄存器的时候我们要的是前者，别写反了。

### 多任务共享计数器

```c
/* 错：volatile 管不了 ++ 的原子性 */
volatile int g_count;
g_count++;

/* 对：用临界区 */
taskENTER_CRITICAL();
g_count++;
taskEXIT_CRITICAL();

/* 或者用原子操作 */
__atomic_add_fetch(&g_count, 1, __ATOMIC_SEQ_CST);
```

### 结构体成员

```c
typedef struct {
    uint16_t len;               /* 不需要 */
    volatile uint8_t ready;     /* 中断里改，需要 */
} frame_t;
```

别图省事把整个结构体加 `volatile`，那会让所有成员访问都变慢，还容易跟库函数打架。只加到真正需要的成员上。

## 一个快速判断的方法

不用背规则，问自己两个问题就行：

**第一，这个变量的值，会不会被编译器看不到的地方改变？** 中断、DMA、硬件、其他任务，都是"看不到的地方"。是，就加。

**第二，这个读写本身有副作用吗？** 读清标志、写触发动作，这种也是。是，就加。

两个问题任意一个是"是"，就加 `volatile`。两个都是"否"，就别加。

还有一句得单独强调：如果这个变量还需要原子地读-改-写，光加 `volatile` 不够，还得上临界区或者原子操作。

## 顺口溜

最后送个口诀，方便记：

> 中断 DMA 和硬件，多任务里共享变；
> 读有副作用，写有触发，一律 volatile 不能免。
> 但它只管"真读写"，原子顺序它不管。

## 收个尾

`volatile` 这关键字说复杂也不复杂，核心就是"别让编译器自作聪明"。真正难的是分清哪些场景需要它、哪些场景需要的是原子操作或者内存屏障——很多人把这三者混为一谈，出的 bug 就特别隐蔽。

我自己吃过最亏的一次，是一个 DMA 接收缓冲区忘了加 `volatile`，单独测试怎么都好使，一到高负载就丢数据，查了整整两天。后来翻汇编才看出来，编译器把几次读合并成了一次。这种事，看代码是看不出来的，只能靠一开始就写对。
